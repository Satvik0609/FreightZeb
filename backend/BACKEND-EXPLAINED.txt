1. PROJECT OVERVIEW
================================================================================

FreightZen is a logistics SaaS platform connecting:
  - WAREHOUSE users  → create shipments, request bookings
  - DEALER users     → register trucks, accept/manage bookings, track deliveries
  - ADMIN            → full platform oversight

The backend is a REST API built with:
  - Node.js + Express                → HTTP server
  - Prisma ORM + PostgreSQL          → data persistence
  - Socket.io                        → real-time events (tracking, notifications)
  - JWT                              → stateless authentication
  - bcryptjs                         → password hashing
  - Winston                          → structured logging
  - node-cron                        → background task scheduling
  - Multer                           → file upload handling
  - Python FastAPI ML service        → predictions (optional, has fallbacks)

No paid third-party APIs are required. Everything runs locally.

3. ENVIRONMENT VARIABLES (.env)
================================================================================

Required (app crashes without these):
  DATABASE_URL  → PostgreSQL connection string
                  Example: postgresql://user:pass@localhost:5432/freightzeb
  JWT_SECRET    → Minimum 32 characters. Used to sign JWT tokens.
                  Generate: openssl rand -hex 32

Optional (defaults applied if missing):
  PORT          → default 5000
  NODE_ENV      → default "development"
  JWT_EXPIRES_IN → default "7d"
  FRONTEND_URL  → default "http://localhost:3000" (used for CORS)
  ML_SERVICE_URL → default "http://localhost:8000" (Python ML service)

Email (SMTP — all optional, emails log to console in dev if not set):
  SMTP_HOST / SMTP_PORT / SMTP_SECURE
  SMTP_USER / SMTP_PASS / SMTP_FROM

Docker only:
  POSTGRES_USER / POSTGRES_PASSWORD / POSTGRES_DB

================================================================================
4. ENTRY POINT — server.js
================================================================================

Execution order on startup:

  1. require('dotenv').config()         → loads .env into process.env
  2. validateEnv()                      → crashes early if required vars missing
  3. Create Express app + HTTP server
  4. Create Socket.io server attached to HTTP server
  5. Apply security middleware:
       helmet()        → sets HTTP security headers
       compression()   → gzip responses
       cors()          → allow FRONTEND_URL or * in dev
       express.json()  → parse JSON bodies up to 2MB
  6. Apply utility middleware:
       requestId       → UUID per request for log tracing
       morgan          → HTTP access logs via Winston
  7. Serve /uploads as static files
  8. Apply rate limiting to all /api/* routes
  9. Share io instance: app.set('io', io)
  10. Register health check: GET /health
  11. Mount 13 route modules under /api/*
  12. Register 404 handler + global error handler
  13. Setup Socket.io connection handler (join/leave rooms)
  14. bootstrap() → connectDB() → startAllJobs() → listen on PORT

Graceful shutdown:
  - SIGTERM / SIGINT → closes HTTP server, disconnects DB, exits cleanly
  - Force exits after 10 seconds if connections don't close

────────────────────────────────────────
5.1  src/config/env.js
────────────────────────────────────────

WHAT IT DOES:
  Validates required environment variables BEFORE any other code runs.
  If DATABASE_URL or JWT_SECRET are missing → prints error → process.exit(1)
  If JWT_SECRET < 32 chars → crashes
  Applies default values to optional vars so the rest of the app
  can safely read process.env.PORT etc. without null checks.

WHY IT MATTERS:
  Failing fast at boot is better than mysterious runtime errors later.
  Called as the FIRST thing in server.js.

CODE:
  const REQUIRED = ['DATABASE_URL', 'JWT_SECRET'];

  function validateEnv() {
    const missing = REQUIRED.filter(key => !process.env[key]);
    if (missing.length > 0) { console.error(...); process.exit(1); }
    // Apply optional defaults
    Object.entries(OPTIONAL_DEFAULTS).forEach(([key, val]) => {
      if (!process.env[key]) process.env[key] = val;
    });
    if (process.env.JWT_SECRET.length < 32) process.exit(1);
  }

────────────────────────────────────────
5.2  src/config/db.js
────────────────────────────────────────

WHAT IT DOES:
  Creates a singleton PrismaClient instance used by all controllers/services.
  In development: logs any query taking > 500ms as a slow query warning.
  Exports connectDB() and disconnectDB() used by server.js bootstrap.

HOW PRISMA WORKS:
  Prisma is an ORM (Object Relational Mapper).
  Instead of writing raw SQL, you write:
    await prisma.user.findUnique({ where: { email } })
  Prisma translates this to SQL and returns typed JS objects.

CODE KEY PARTS:
  const prisma = new PrismaClient({ log: [...], errorFormat: 'minimal' });
  prisma.$on('query', (e) => { if (e.duration > 500) logger.warn(...) });
  async function connectDB() { await prisma.$connect(); }
  module.exports = { prisma, connectDB, disconnectDB };

────────────────────────────────────────
5.3  src/config/logger.js
────────────────────────────────────────

WHAT IT DOES:
  Creates a Winston logger that writes structured JSON logs.
  In development: also prints colored readable output to console.
  Files:
    logs/error.log      → only ERROR level, max 10MB × 5 rotations
    logs/combined.log   → all levels, max 20MB × 10 rotations
    logs/exceptions.log → uncaught exceptions
    logs/rejections.log → unhandled promise rejections

USAGE ACROSS CODEBASE:
  const logger = require('../config/logger');
  logger.info('User registered');
  logger.warn('ML service unavailable — using fallback');
  logger.error('DB connection failed', { stack: err.stack });

6. DATABASE SCHEMA (prisma/schema.prisma)
================================================================================

All IDs are UUIDs (auto-generated). All timestamps are UTC DateTime.

────────────────────────────────────────
6.1  User model
────────────────────────────────────────

Fields:
  id                  UUID primary key
  email               unique, used for login
  password            bcrypt hash (never stored as plain text)
  name                display name
  role                enum: ADMIN | WAREHOUSE | DEALER
  phone               optional
  company             optional
  avatarUrl           optional, path to uploaded avatar file
  passwordResetToken  SHA-256 hash of reset token (not the raw token)
  passwordResetExpiry DateTime, 1 hour after token creation
  isActive            boolean, admin can deactivate accounts
  createdAt/updatedAt auto-managed

Relations:
  shipments           → Shipment[] (as warehouse owner)
  trucks              → Truck[]   (as dealer owner)
  bookingsAsWarehouse → Booking[] (shipments I booked)
  bookingsAsDealer    → Booking[] (my trucks were booked)
  notifications       → Notification[]
  invoices            → Invoice[]  (billed to this user)

────────────────────────────────────────
6.2  Shipment model
────────────────────────────────────────

Fields:
  id              UUID
  warehouseId     FK → User (the warehouse that created it)
  weightKg        float, required
  volumeM3        float, optional
  boxes           int, optional
  pickupLocation  JSON: { lat, lng, address, city, pincode }
  destination     JSON: { lat, lng, address, city, pincode }
  deadline        optional DateTime
  description     optional text
  requirements    optional JSON: { hazardous, fragile, tempControlled, oversized }
  status          enum: PENDING | OPTIMIZED | BOOKED | IN_TRANSIT | DELIVERED | CANCELLED

Relations:
  warehouse  → User
  bookings   → Booking[]
  predictions → Prediction[]

────────────────────────────────────────
6.3  Truck model
────────────────────────────────────────

Fields:
  id              UUID
  dealerId        FK → User (dealer who owns it)
  registrationNo  unique string (e.g. "MH12AB1234")
  truckType       enum: SMALL_VAN | CONTAINER_20FT | CONTAINER_32FT | FLATBED_TRAILER | REEFER
  capacityKg      float
  capacityM3      optional float
  routeFrom       string (source city)
  routeTo         string (destination city)
  availability    boolean flag
  pricePerKm      optional float (₹/km, overrides system rates)
  currentLocation JSON: { lat, lng, lastUpdated }  — updated via GPS endpoint
  status          enum: AVAILABLE | BOOKED | IN_TRANSIT | MAINTENANCE

Relations:
  dealer       → User
  bookings     → Booking[]
  trackingLogs → TrackingLog[]

────────────────────────────────────────
6.4  Booking model
────────────────────────────────────────

Fields:
  id           UUID
  shipmentId   FK → Shipment
  truckId      FK → Truck
  warehouseId  FK → User (who requested booking)
  dealerId     FK → User (whose truck it is)
  status       enum: REQUESTED | APPROVED | REJECTED | ASSIGNED | PICKED_UP | IN_TRANSIT | DELIVERED | CANCELLED
  optimScore   optional float 0-1 (from optimization engine)
  distanceKm   computed on creation via Haversine formula
  pricing      JSON: full pricing breakdown (baseCharge, gst, total, etc.)
  estimatedEta DateTime computed on creation
  pickedUpAt   set when status → PICKED_UP
  deliveredAt  set when status → DELIVERED
  notes        optional text
  proofOfDelivery JSON: { photos: [url], signature: url, submittedAt }

Relations:
  shipment     → Shipment
  truck        → Truck
  warehouse    → User
  dealer       → User
  trackingLogs → TrackingLog[]
  invoice      → Invoice (auto-created on DELIVERED)

────────────────────────────────────────
6.5  TrackingLog model
────────────────────────────────────────

Fields:
  id         UUID
  bookingId  FK → Booking
  truckId    FK → Truck
  latitude   float
  longitude  float
  status     optional string (human-readable note e.g. "Near Nagpur")
  timestamp  auto set to now()

One row per GPS ping. History is queryable by bookingId.

────────────────────────────────────────
6.6  Notification model
────────────────────────────────────────

Fields:
  id        UUID
  userId    FK → User (recipient)
  type      string constant e.g. "BOOKING_REQUESTED", "SHIPMENT_DELIVERED"
  title     short heading
  message   full text
  meta      optional JSON: { bookingId, shipmentId }
  isRead    boolean default false
  createdAt auto

────────────────────────────────────────
6.7  Invoice model
────────────────────────────────────────

Fields:
  id        UUID
  bookingId unique FK → Booking (one invoice per booking)
  userId    FK → User (billed to warehouse)
  invoiceNo unique string e.g. "INV-1713200000000"
  pricing   JSON (copied from Booking.pricing at time of delivery)
  status    enum: PENDING | PAID | OVERDUE | CANCELLED
  issuedAt  auto (now)
  paidAt    set by admin via PATCH /api/invoices/:id/pay
  dueDate   7 days after issuedAt
  notes     optional

Auto-created when booking status changes to DELIVERED (inside DB transaction).

────────────────────────────────────────
6.8  Prediction model
────────────────────────────────────────

Fields:
  id           UUID
  shipmentId   FK → Shipment
  type         enum: ETA_HOURS | DELAY_RISK_PERCENT | RECOMMENDED_TRUCK_SCORE | FUEL_ESTIMATE_LITERS | CO2_KG
  value        float
  confidence   optional float 0-1
  modelVersion optional string

Populated by the runOptimization endpoint. Stores ML predictions alongside shipments.

7. MIDDLEWARE
================================================================================

────────────────────────────────────────
7.1  src/middleware/authMiddleware.js
────────────────────────────────────────

protect(req, res, next):
  - Reads Authorization header: "Bearer <token>"
  - Verifies JWT using process.env.JWT_SECRET
  - On success: attaches decoded { id, email, role } to req.user, calls next()
  - On failure: 401 Unauthorized

restrictTo(...roles):
  - Returns a middleware function
  - Checks if req.user.role is in the allowed roles array
  - On success: calls next()
  - On failure: 403 Forbidden with message "Required role: X or Y"

Usage in routes:
  router.post('/', protect, restrictTo('WAREHOUSE', 'ADMIN'), createShipment);

────────────────────────────────────────
7.2  src/middleware/errorMiddleware.js
────────────────────────────────────────

notFound(req, res, next):
  - Catches any route that wasn't matched
  - Creates a 404 error and forwards to errorHandler

errorHandler(err, req, res, next):
  - Central error handler for the whole app
  - Handles specific Prisma error codes:
      P2002 → 409 "A record with this value already exists" (unique constraint)
      P2025 → 404 "Record not found"
      P2003 → 400 "Related record not found" (foreign key violation)
  - In production: hides internal error messages (shows "Internal server error")
  - In development: exposes full stack trace in response
  - Logs all 500 errors with full context to Winston

────────────────────────────────────────
7.3  src/middleware/rateLimiter.js
────────────────────────────────────────

authLimiter:
  - Applied to: POST /api/auth/register, /api/auth/login, /api/auth/forgot-password
  - Limit: 20 requests per 15 minutes per IP
  - Prevents brute force attacks on auth endpoints

apiLimiter:
  - Applied to: all /api/* routes
  - Limit: 100 requests per minute per IP
  - Returns 429 Too Many Requests when exceeded

────────────────────────────────────────
7.4  src/middleware/upload.js
────────────────────────────────────────

Built on Multer. Saves files to local disk (backend/uploads/).

Allowed file types: jpeg, jpg, png, webp, pdf
Max file size: 5MB

Storage structure:
  uploads/
    avatars/           ← user profile photos
    proof-of-delivery/ ← delivery evidence photos + signatures
    documents/         ← shipment PDFs

Each file gets a unique name: {timestamp}-{random}.ext

Three middleware factories (set req.uploadFolder):
  proofOfDeliveryUpload → folder = "proof-of-delivery"
  avatarUpload          → folder = "avatars"
  documentUpload        → folder = "documents"

────────────────────────────────────────
7.5  src/middleware/validate.js
────────────────────────────────────────

Runs express-validator's validationResult(req).
If there are errors → returns 422 with array of field errors + messages.
If no errors → calls next().

Usage after validator arrays in routes:
  router.post('/', authLimiter, registerRules, validate, register);

────────────────────────────────────────
7.6  src/middleware/requestId.js
────────────────────────────────────────

Attaches a UUID to each incoming request as req.requestId.
Also sets the X-Request-ID response header.
Used in error responses and logs for cross-referencing.

ROUTE DESIGN PATTERNS:
  1. Named/specific paths ALWAYS before parameterised paths
     e.g. GET /my and GET /available must come before GET /:id
     because Express matches top-to-bottom and /:id would consume "my"
  
  2. router.use(protect) / router.use(protect, restrictTo('ADMIN'))
     applies middleware to ALL subsequent routes in that router
  
  3. Validators run before controllers:
     router.post('/', protect, restrictTo('WAREHOUSE'), createShipmentRules, validate, createShipment)

9. CONTROLLERS
================================================================================

Controllers contain the actual business logic for each route.
They receive (req, res, next), do DB operations, call services, and respond.
All errors are forwarded to next(err) for the global error handler.

────────────────────────────────────────
9.1  authController.js
────────────────────────────────────────

register(req, res, next):
  1. Check if email already exists → 409 if so
  2. Hash password with bcrypt (cost factor 12)
  3. Create user in DB
  4. Sign JWT token (contains id, email, role)
  5. Send welcome email (async, non-blocking)
  6. Return 201 with token and user object

login(req, res, next):
  1. Find user by email → 401 if not found or not active
  2. Compare submitted password with bcrypt hash → 401 if mismatch
  3. Sign JWT token
  4. Return 200 with token and user object

getMe(req, res, next):
  - Fetches full user by req.user.id (set by protect middleware)
  - Returns user without password field
  - Uses Prisma select to whitelist returned fields

updateMe(req, res, next):
  - Only allows changing: name, phone, company
  - Email and role cannot be changed here (admin-only via /api/admin)

changePassword(req, res, next):
  1. Verify currentPassword matches stored hash
  2. Hash newPassword
  3. Update in DB
  Note: Does NOT invalidate existing JWT tokens. For production, add
  a passwordChangedAt field and validate in protect() middleware.

forgotPassword(req, res, next):
  1. Generate 32-byte random token with crypto.randomBytes()
  2. SHA-256 hash the token, store hash in DB (not the raw token)
  3. Set expiry to 1 hour from now
  4. Send email with the RAW token as reset link
  5. Always returns the same generic message (prevents email enumeration)

resetPassword(req, res, next):
  1. Hash the submitted token (same SHA-256)
  2. Find user where stored hash matches AND expiry > now
  3. Hash new password, update user, clear reset token fields
  WHY HASH THE TOKEN: If DB is leaked, the raw tokens are still safe.

────────────────────────────────────────
9.2  truckController.js
────────────────────────────────────────

createTruck:
  - Sets dealerId = req.user.id automatically
  - Initial status is AVAILABLE, availability = true
  - Registration numbers are unique (P2002 Prisma error caught → 409)

getMyTrucks:
  - Filtered by dealerId = req.user.id
  - Supports query params: status, page, limit (pagination)

getAllTrucks (ADMIN):
  - Supports filtering: status, truckType, dealerId
  - Includes dealer info in response

getAvailableTrucks:

9.4  bookingController.js
────────────────────────────────────────

createBooking: (the most complex endpoint)
  1. Fetch shipment and truck in parallel (Promise.all)
  2. Validate:
     - Shipment must belong to requesting warehouse
     - Truck must be AVAILABLE
     - Shipment must not already be BOOKED/IN_TRANSIT/DELIVERED/CANCELLED

  4. Create estimated ETA: now + durationMin
  5. Calculate pricing breakdown (pricingService.calculate)

     - Create booking with status REQUESTED
     - Update shipment status to BOOKED

  Valid transitions:
    REQUESTED  → APPROVED, REJECTED, CANCELLED
    APPROVED   → ASSIGNED, CANCELLED
    ASSIGNED   → PICKED_UP, CANCELLED
    PICKED_UP  → IN_TRANSIT
    IN_TRANSIT → DELIVERED

  Role enforcement:
    APPROVED, REJECTED, ASSIGNED  → only DEALER or ADMIN
    CANCELLED                     → only WAREHOUSE or ADMIN
    PICKED_UP, IN_TRANSIT, DELIVERED → only DEALER or ADMIN

    APPROVED   → truck status → BOOKED
    PICKED_UP/IN_TRANSIT → truck → IN_TRANSIT, shipment → IN_TRANSIT
    DELIVERED  → truck → AVAILABLE, shipment → DELIVERED, AUTO-CREATE INVOICE
    CANCELLED/REJECTED → truck → AVAILABLE, shipment → PENDING

  After transaction:
    - Socket.io events to booking room and warehouse room
    - Notifications + emails for APPROVED, REJECTED, PICKED_UP, DELIVERED

10.3  mlService.js  (THE MOST IMPORTANT SERVICE)
────────────────────────────────────────

Communicates with the Python FastAPI ML microservice at ML_SERVICE_URL.
Uses axios with a 10-second timeout. Every method has a heuristic fallback.

ML Microservice Endpoints it calls:
  POST /predict              → unified dispatcher
  POST /predict-truck        → truck recommendation
  POST /predict-delivery-time → delivery ETA
  POST /predict-delay-risk   → delay risk
  GET  /estimate-fuel        → fuel estimation
  POST /cluster-shipments    → shipment clustering
  POST /optimize-cargo       → cargo optimisation
  GET  /health               → health check
  GET  /models/info          → model metadata

HOW FALLBACKS WORK:
  try {
    const res = await axios.post(`${ML_API_URL}/predict-truck`, body, { timeout: 10000 });
    return res.data;     // ML worked → return ML result
  } catch (err) {
    logger.warn('ML unavailable — using fallback');
    return this._truckFallback(data);  // use math-based heuristic
  }

Fallback heuristics:
  _truckFallback:    Rules based on weight/volume/cargo type
  _deliveryFallback: distance_km / 60 km/h average speed
  _fuelFallback:     distance_km × fuel_rate_per_km (by truck type)
  _delayFallback:    weather risk % + traffic risk % (lookup tables)

CO2 estimation:
  estimateCo2(distanceKm, truckType)
    → Uses hardcoded kg CO2 per km rates (no ML needed, pure math)
    SMALL_VAN=0.18, CONTAINER_20FT=0.55, CONTAINER_32FT=0.72, REEFER=0.90

────────────────────────────────────────
10.4  optimizationService.js
────────────────────────────────────────

Multi-step pipeline to rank available trucks for a shipment.

Step 1: loadCandidates(shipment)
  → DB query: all trucks where status=AVAILABLE and availability=true

Step 2: filterTrucks(trucks, shipment)
  Hard filters:
  - truck.capacityKg >= shipment.weightKg
  - truck.capacityM3 >= shipment.volumeM3 (if both set)
  - If truck has routeFrom/routeTo set, shipment cities must match (loose match)

Step 3: scoreTruck(truck, shipment, distanceKm)
  Scores 4 dimensions (0 to 1 each):
  
  utilizationScore     (weight 35%)
    = (weight_fill + volume_fill) / 2
    Best truck is the one that uses its capacity most efficiently
  
  distanceMatchScore   (weight 25%)
    = 1 / (1 + distanceKm / 500)
    Shorter routes score higher (exponential decay)
  
  costEfficiencyScore  (weight 25%)
    = min(50 / pricePerKm, 1.0)
    Cheaper trucks score higher (baseline ₹50/km)
  
  co2Score             (weight 15%)
    = 1 - co2PerKm / maxCo2
    Less polluting trucks score higher

  composite = 0.35×util + 0.25×dist + 0.25×cost + 0.15×co2

Step 4: Sort by composite score descending, return top 5

────────────────────────────────────────
10.5  pricingService.js
────────────────────────────────────────

Calculates freight cost breakdown for a shipment.

Inputs: distanceKm, weightKg, truckType, dealerPricePerKm

Base rates per km (₹):
  SMALL_VAN=12, CONTAINER_20FT=28, CONTAINER_32FT=38, FLATBED_TRAILER=42, REEFER=55

Calculation:
  ratePerKm    = dealer's rate if set, otherwise base rate
  baseCharge   = max(ratePerKm × distanceKm, ₹500 minimum)
  weightExtra  = (weightKg - 5000) × ₹0.80/kg (if over 5000 kg)
  fuelSurcharge = baseCharge × 8%
  subtotal     = baseCharge + weightExtra + fuelSurcharge
  gst          = subtotal × 18%
  total        = subtotal + gst

Returns full breakdown JSON stored in booking.pricing.

13. REQUEST / RESPONSE FLOW (end-to-end example)

Example: POST /api/bookings  (Warehouse creates a booking)

14. AUTH & ROLE-BASED ACCESS CONTROL

================================================================================
15. BOOKING LIFECYCLE STATE MACHINE
================================================================================

States and valid transitions:

  REQUESTED ──→ APPROVED (by DEALER)
             ──→ REJECTED (by DEALER)
             ──→ CANCELLED (by WAREHOUSE)

  APPROVED ──→ ASSIGNED (by DEALER)
           ──→ CANCELLED (by WAREHOUSE)

  ASSIGNED ──→ PICKED_UP (by DEALER, truck physically loads shipment)
           ──→ CANCELLED

  PICKED_UP ──→ IN_TRANSIT (by DEALER, truck departs)

  IN_TRANSIT ──→ DELIVERED (by DEALER, delivery confirmed)

  DELIVERED → FINAL STATE (auto-creates invoice)
  REJECTED  → FINAL STATE
  CANCELLED → FINAL STATE (truck + shipment reset to AVAILABLE/PENDING)

Side effects at each transition (done in DB transaction):
  APPROVED   → Truck.status = BOOKED
  PICKED_UP  → Truck.status = IN_TRANSIT, Shipment.status = IN_TRANSIT
  IN_TRANSIT → Same as PICKED_UP
  DELIVERED  → Truck.status = AVAILABLE, Shipment.status = DELIVERED
               + Invoice auto-created with 7-day due date
  CANCELLED  → Truck.status = AVAILABLE, Shipment.status = PENDING

================================================================================
16. ML SERVICE INTEGRATION & FALLBACKS
================================================================================

Architecture:
  Client → Node.js Backend → Python FastAPI ML Service (localhost:8000)
                           ↘ Heuristic fallback (if ML offline)

The ML service has 6 prediction models:
  1. Truck Recommendation     → which truck type to use
  2. Delivery Time Prediction → ETA in hours
  3. Delay Risk Assessment    → probability of delay
  4. Fuel Estimation          → liters + cost + CO2
  5. Shipment Clustering      → group shipments for batch routing
  6. Cargo Optimization       → bin-packing for maximum utilization

Fallback behavior:
  Every ML call is wrapped in try/catch.
  If the Python service is:
    - Down (connection refused)
    - Slow (> 10 second timeout)
    - Returning errors
  → the backend automatically uses mathematical heuristics
  → all fallback responses include { "fallback": true } field
  → the API still returns 200 OK (never fails because of ML)

This means the entire backend works even without the ML service running.

================================================================================
18. ERROR HANDLING STRATEGY
================================================================================

Level 1: Validator errors (422 Unprocessable Entity)
  express-validator catches malformed request data before hitting controllers.

Level 2: Business logic errors (4xx)
  Controllers explicitly return specific status codes:
  - 400 Bad Request     → invalid state transitions, logical errors
  - 401 Unauthorized    → missing/invalid JWT
  - 403 Forbidden       → valid auth but insufficient permissions
  - 404 Not Found       → record doesn't exist
  - 409 Conflict        → duplicate unique field

Level 3: Prisma errors (automatically mapped in errorHandler)
  P2002 → 409  (unique constraint violated)
  P2025 → 404  (record not found)
  P2003 → 400  (foreign key constraint failed)

Level 4: Unexpected errors (500)
  Any unhandled error propagated via next(err).
  In production: returns generic "Internal server error" message.
  In development: returns full error + stack trace.

Level 5: Process-level errors
  uncaughtException and unhandledRejection → logged → process.exit(1)
  These crash the process intentionally (let process manager like PM2 restart it).
